# Phase 6 / 6b Report — Manufacturing and antisera extension

## What was implemented
* **BOM (§33, BR-BOM-001/002)** — versioned BOM (header + lines + master-batch-record steps) on the common versioning engine: draft-only editing, submit, **QA Head e-signature approval** (author ≠ approver, SOD-25), supersede, new-version copy (lines and steps), point-in-time lookup. Only ACTIVE products/components; FG cannot be a BOM input; no self-reference or duplicates. Products are Materials of type SFG/FG (single master).
* **Batches (§34, BR-BAT-001/002, BR-BOM-001)** — require an approved, in-force BOM which is **pinned**; automatic numbering (SFG/FG sequences); manual batch-number override needs `mfg.batch.override_number` + reason and is checked for uniqueness against batches *and* lots; DB uniqueness; cancelled numbers stay on record. Requirements are scaled from the BOM (with overage) and an indent is generated.
* **Issue (§35, BR-ISS-001…007, BR-TRC-001, BR-HOLD-001/002)** — lot must be released, unexpired, not on hold, and the *material required by the BOM line*; quantity ≤ required unless an authorised additional issue; **FEFO/FIFO deviation needs a reason** (BR-ISS-005); an unreleased lot may be used **only** under an approved conditional release for that batch and within its quantity (BR-CRL-003) and the batch is flagged "USED UNDER QA-AUTHORIZED CONDITIONAL RELEASE". Each issue is an append-only `material_issue` row referencing both lot and batch (NOT NULL FKs) plus the `ISSUE` ledger transaction.
* **Returns (BR-RET-001)** — request (used + returned + damaged ≤ issued) → accepted by a different person (SOD-26); the returned stock re-enters via a `RETURN` ledger transaction under the quarantine/approved location rules.
* **Process execution (BR-MFG-001…004)** — line clearance e-signature starts processing only when all materials are issued; MBR steps are snapshotted from the pinned BOM, executed in order without overwrite, critical steps verified by a second person with e-signature (SOD-27); equipment must be qualified, calibrated and cleaned; **IPC** results (append-only) auto-evaluated — a failure places the batch on **hold** and notifies QA/production; held batches cannot complete.
* **Reconciliation (§68, BR-REC-001, critical rule 15)** — per material: issued = consumed + sampled + waste + returned + unaccounted; variance % vs configurable tolerance (`recon.tolerance_pct`, default 0.5); yield % vs BOM limits. Within tolerance → production approval completes it; otherwise production approval *and* a QA Head approval with deviation reference + justification by a different person (SOD-28) are required before output can be booked.
* **Output** — output lot created in an active quarantine location with `OUTPUT` ledger transaction, shelf life from the product master and the specification in force pinned; the batch moves to QC_QA. The Phase 5 release chain then drives the lot to APPROVED/REJECTED and the batch to RELEASED/REJECTED (hook `manufacturing.on_lot_released`). **BR-CRL-004**: release readiness fails while any conditionally-released source lot is not finally APPROVED.
* **Antisera (6b)** — donor animals (audited), append-only immunisation records, bleeds with minimum interval enforcement (BR-ANM-002), plasma pools that create a quarantined `POOL` lot (ledger `OUTPUT`) and keep bleed→animal genealogy (BR-ANM-003: a bleed joins one pool only).
* **Frontend** — BOM (create/approve/new version), Manufacturing Batches (issue with FEFO suggestions, line clearance, step execution/verification, IPC, consumption, reconciliation view with red discrepancies, QA deviation approval, output), Material Returns, Antisera. `GET /materials` gained a `type_code` filter.

## Known limitations
1. SFG→FG consumption works through the normal issue of an APPROVED SFG lot (same mechanism); there is no dedicated multi-stage routing or work-order scheduling.
2. MBR steps are free-text instructions with an optional recorded value; no electronic step templates with typed parameters/limits (IPC covers limits).
3. Theoretical-yield uses the BOM batch size scaling; no co-product/by-product modelling.
4. Plasma pools assume the plasma material's base unit is litres (not enforced); no donor health/vaccination schedule or titre tracking.
5. Additional issue requires the `mfg.issue.additional` permission but not a separate signed approval record.
6. Equipment cleaning is a confirmation flag, not a cleaning-log record linked to cleaning SOPs.
