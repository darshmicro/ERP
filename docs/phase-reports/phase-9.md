# Phase 9 Report — Reports, dashboards, retention, backup status and controlled printouts

## What was implemented
* **Report engine (§50, §66)** — a registry of **37 permissioned, parameterised reports** (`app/reports/catalog.py`), each declaring its read permission, typed parameters (date / number / choice / required) and business columns. Output as on-screen JSON preview, **XLSX** (header with company, title, filters, user, time), **CSV** (UTF-8 BOM) and **PDF** (landscape table; company logo/name, filters, record count). Server-side parameter validation (422 on bad dates / choices / missing required parameters). Groups: Purchase (vendor list, qualification status, AVL, PR, PO, pending receipt), Warehouse/Inventory (GRN, stock status, ledger, ledger-vs-balance integrity check, quarantine ageing, expiry forecast, holds, temperature excursions, destruction), QC (pending, results, OOS, OOT, CoA, conditional releases, equipment calibration), Manufacturing (batch register, material issues, reconciliation/yield, IPC), Dispatch (register, **lot genealogy**), Quality (deviation, CAPA, change control, complaints+recalls, SOP), System (audit trail, e-signature log, user access, security events).
* **Report permission and field-leak controls** — the catalogue lists only reports whose own permission the caller holds; running or exporting without it is `403`; exports additionally need `reports.export.run`; no report exposes password hashes, secrets or tokens (asserted by test over every catalogue column and the user-access output).
* **Controlled copies / printed-copy control (Annex 11 §8, Part 11.10(b))** — every export or business-document print gets a **controlled-copy number** (`RPT-yyyy-nnnnnn`), is logged **append-only** (`report_run`: user, report, parameters, format, rows, SHA-256 of the output) and appears in the audit trail; PDFs carry the copy number, printing user and time in the footer. `GET /reports-verify` confirms that a presented file's hash matches the recorded one.
* **Controlled business documents (PDF)** — purchase order, GRN, dispatch note and **batch manufacturing record** (materials, issues incl. FEFO deviations and conditional release flags, executed/verified steps with names and times, IPC, reconciliation, e-signature block).
* **Dashboards (§90)** — Management, QC, QA and Warehouse (role-gated `dashboard.<name>.read`): KPI cards with warning/danger tones plus bar series (batches by status, deviations by severity, lots by disposition, samples/OOS status, holds by source, stock by material type, …). Home cards extended (open deviations/CAPA/overdue).
* **Retention and archival (§81, BR-RET-001/002)** — policy per record type (10 seeded with regulatory basis text), cut-off derivation, eligible-record counts, **legal hold** (reason required), periods can **only be extended** in-app, and **non-destructive archive packages** (contiguous, non-overlapping blocks of ≤ 100 000 records past the cut-off, recorded with first/last id; XLSX, SHA-256, stored as a write-once controlled document; download re-verifies the hash; re-run until nothing is left). The application never deletes GMP records.
* **Backup status page (§82)** — append-only evidence of FULL / DIFFERENTIAL / LOG / DOCUMENTS backups and **restore tests** (incl. audit-chain-verified flag and measured RTO); alerts when the newest successful backup is older than `backup.max_age_hours` (26 h) or no restore test within `backup.restore_test_days` (180 d); on SQL Server it also tries to read `msdb.dbo.backupset` when permitted.
* **Frontend** — Reports (catalogue by group, parameter form, preview, XLSX/CSV/PDF export with copy number), Dashboards (tabs, cards, charts), Retention & Backup (backup evidence form, policy table with extend/hold/archive, archive download, copy verification, controlled-copy log); "Print PDF" buttons on PO, GRN, dispatch and batch dialogs.

## Database
Migration `0009`: `report_run`*, `retention_policy`, `archive_batch`*, `backup_record`* (* append-only with DB triggers). Retention defaults are seeded by `seed_baseline` (re-run `scripts/bootstrap_admin` on an upgraded database to add them).

## Tests
`tests/workflows/test_reports.py` — **8 passed**: all catalogue reports run against a real end-to-end world and give correct content (dispatch register, stock status, ledger, batch register, reconciliation, genealogy, ledger-vs-balance = 0 differences); permission/parameter/field-leak/unauthenticated tests; XLSX/CSV/PDF exports with unique controlled-copy numbers, hash verification (match / mismatch / unknown), append-only run log and audit entries; PO/GRN/dispatch/batch-record PDFs; dashboards (role gating and values); retention (never shorten, admin cannot change, archive creation + verified download, originals untouched, legal hold); backup evidence rules and alerts; **performance** with 5 000 ledger rows (preview < 10 s, CSV < 15 s, XLSX < 20 s on the test host).

## Known limitations
1. Reports are computed on demand (no scheduled/emailed reports, no saved report definitions, no ad-hoc report builder); preview is capped (5 000 rows), exports 50 000 rows (audit/e-signature/security reports 20 000 newest).
2. PDF layouts are fixed templates (no site-specific document numbering/format control for PO/GRN/dispatch printouts beyond company name and logo); CoA remains the Phase 5 template.
3. Archive packages are Excel files — adequate for retrieval and verification, but not an immutable WORM store; moving them to write-once storage and physically purging live data are site/DBA procedures (documented in the Administrator manual).
4. The backup page records *evidence*; it cannot trigger or verify backups itself (SQL Server `msdb` look-up needs extra rights that the application login intentionally does not have).
5. Dashboards are snapshots without drill-down links or time-range selection; no trend history is stored.
6. The 5 000-row performance check is a smoke test, not the 100 k-row/50-user load test planned for Phase 10.
