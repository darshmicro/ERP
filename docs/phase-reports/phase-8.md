# Phase 8 Report — Quality system

## What was implemented
* **Deviation (§55)** — OPEN → INVESTIGATION → CAPA_PROPOSED → QA_REVIEW → CLOSED (+ Cancelled; QA can return to investigation). Root cause and impact assessment are mandatory to propose a CAPA; a MAJOR/CRITICAL deviation needs a linked CAPA *or* a documented justification (BR-DEV-002). Closure by QA Head with e-signature; **raiser cannot close** (SOD-31). A deviation linked to a lot or production batch **blocks QA release (readiness check) and dispatch** while open (BR-DEV-001 / BR-DSP-004) unless flagged non-blocking.
* **Automatic deviations** — IPC failure, temperature excursion (per lot) and reconciliation discrepancy raise deviations (idempotent while open). The Phase 6 QA acceptance of an out-of-tolerance reconciliation now **must reference a real deviation record** (BR-REC-001); the auto-raised one is used by default.
* **CAPA (§56)** — owner, due date, actions with owners/due dates, OPEN → IN_PROGRESS → EFFECTIVENESS_CHECK → CLOSED; effectiveness check requires all actions done; an *ineffective* outcome re-opens it; QA Head e-signature to close, creator ≠ closer (SOD-34); linked to deviations; overdue detection and daily alerts.
* **Change control (§57, BR-BOM-002, BR-VM-001, BR-CC-001)** — DRAFT → ASSESSMENT (impact + risk level) → APPROVAL (QA Head e-signature, requester ≠ approver SOD-32, rejection possible) → IMPLEMENTATION → EFFECTIVENESS → CLOSED. Changes are **linked to the new draft version of a controlled master** (specification, STP, sampling plan, BOM, vendor–material, SOP). With `cc.required_for_master_changes = true` the approval of any master version > 1 is refused unless an approved change control is linked to it; implementation cannot be declared until the linked versions are APPROVED. (Default is *off* so a site can adopt it deliberately.)
* **Risk assessment / FMEA (§58)** — items with S/O/D (1–10), server-computed RPN and level (configurable thresholds `risk.rpn_high` 200 / `risk.rpn_medium` 100), mitigation and residual risk; HIGH items cannot be approved without mitigation and residual rating (BR-RSK-001); QA Head e-signature, author ≠ approver (SOD-33); approved assessments immutable.
* **SOP control (§59)** — versioned (draft → under review → approved → superseded) on the common versioning engine with QA Head e-signature (SOD-35), PDF attachment hashed (SHA-256, write-once document store), effective dates, periodic **review due** date (`review_period_months`), read-and-understood **acknowledgement** records (append-only, once per user per version), daily review-due alerts.
* **Complaints (§61)** — linked to customer/dispatch/lot (lot must belong to the dispatch); CRITICAL or adverse-event complaints **place the lot on quality hold automatically**; investigation → optional deviation → closure with QA e-signature, blocked while the linked deviation is open (BR-CMP-001).
* **Recall (§62)** — QA Head e-signature initiates; lot held immediately; **affected shipments and customers derived from the dispatch ledger**; customer notification tracking, returns booked back through the ledger into quarantine/rejected locations only (BR-RCL-003), unrecoverable quantities, recovery reconciliation; closure needs all customers notified + e-signature.
* **Dashboard / jobs** — open deviations, open CAPA, overdue CAPA cards; daily job notifies overdue CAPA owners/QA and SOPs due for review.
* **Frontend** — Deviations, CAPA, Change control, Risk (FMEA), SOPs, Complaints, Recalls (generic record dialogs with workflow buttons and e-signature prompts).

`tests/workflows/test_quality_system.py` — **14 tests**: deviation blocks QA release until closed with independent QA signature; raiser cannot close; non-blocking flag; temperature excursion → deviation (idempotent); IPC failure → deviation; reconciliation breach → deviation, bogus reference refused, open deviation blocks the output lot's release; CAPA lifecycle incl. ineffective loop and SoD; change control gating a specification revision (BR-CC-001 → CC flow → approve → implement → close); CC SoD/rejection; FMEA RPN, levels, approval rules, immutability; SOP versioning, document hash, acknowledgement, supersede, review-due; critical complaint hold and deviation-before-closure; recall affected-customer derivation, ledger returns and reconciliation, hold prevents re-dispatch; permissions. Phase 6 reconciliation tests updated for the deviation record requirement.

## Known limitations
1. No dedicated **audit/inspection management** or supplier-audit scheduling; **training matrix** assignment from SOP effectivity is not automated (acknowledgement is recorded; the existing training gate is unchanged).
2. Deviation/CAPA/complaint records are single-document forms: no multi-section approval templates, attachments (use the document store separately), or SLA escalation (alerts only).
3. Deviation linkage is to a lot or a production batch; free-form links (equipment, area, document) are text only. Deviation severity does not yet change workflow chains.
4. CC enforcement (BR-CC-001) is configuration-driven and off by default; vendor qualification versions are exempt (they are requalifications, governed by their own rules).
5. Recall notification is tracked manually (no email/SMS/regulatory-report generation); regulatory timelines (e.g., 24 h/ 72 h reporting) are not modelled.
6. FMEA has no severity-driven action priority tables (AIAG-VDA); RPN thresholds are configurable but the method is classic RPN.
